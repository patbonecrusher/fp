Higher-Order Functions

Separate the loop (mechanism) from what happens on each item (policy) — write the loop once, reuse it forever.

What it is

Ordinary functions operate on data: numbers, strings, objects. A higher-order function treats functions as the data it operates on — it accepts a function as an argument, returns a new function, or both.

You already used one in Lesson 4 without naming it: pipe(f, g, h) takes functions in and hands back a brand-new function. map, filter, and reduce are the most common HOFs of all — this lesson builds one from scratch to see exactly why they exist.

function myFilter(list, predicate) {
  const result = [];
  for (const item of list) {
    if (predicate(item)) result.push(item);
  }
  return result;
}

myFilter doesn't know or care what "adult" or "active" means — it just runs whatever function you hand it against every item. The function you pass in (predicate) is the only thing that changes between calls.

Why it matters

  • One loop, many policies — the iteration logic (how to walk the list, build up a result) is written and tested exactly once, no matter how many different conditions you need.
  • Declarative call sites — users.filter(isAdult) reads as what you want, not a multi-line description of how to get it.
  • Small, composable predicates — conditions like isAdult or notDeleted become reusable, independently testable building blocks, the same way Lesson 4's small functions were.
  • Foundation for everything ahead — currying, memoization, and later the Functor/Monad pattern from the glossary you linked all lean on functions-as-arguments.

This is Lesson 1 and Lesson 4 combined into one habit: write small pure predicates, then let a single trusted HOF do the iterating for all of them.

Watch it break

The setup: a user list includes a soft-deleted account (deleted: true) that should never appear in any filtered list — not the adults list, not the active-users list.

With hand-rolled loops, that rule has to be added to every copy of the loop separately. Someone fixes the adults loop and misses the other one:

function filterAdultsFixed(list) {
  for (const u of list) {
    if (u.age >= 18 && !u.deleted) result.push(u); // fixed here
  }
  ...
}
// filterActiveUsers still has its own separate loop — untouched

Actual output when you run the lesson script:

Monolithic, before excluding soft-deleted users: adults: [ 'Grace', 'Alan', 'Barbara' ] active: [ 'Ada', 'Alan', 'Barbara' ] After fixing the 'exclude deleted' rule in ONE loop: adults: [ 'Grace', 'Barbara' ] active: [ 'Ada', 'Alan', 'Barbara' ] <-- Alan (deleted) still slipped through Higher-order, before excluding soft-deleted users: adults: [ 'Grace', 'Alan', 'Barbara' ] active: [ 'Ada', 'Alan', 'Barbara' ] After adding the 'exclude deleted' rule to both predicates: adults: [ 'Grace', 'Barbara' ] active: [ 'Ada', 'Barbara' ] <-- Alan correctly excluded everywhere

With myFilter, there's only ever one loop. Fixing "exclude deleted users" means writing one small predicate (notDeleted) and combining it into each policy — there's no second copy of the loop left to forget about.

Related concepts

Pure Functions

A HOF is only predictable if the functions passed into it are pure — an impure predicate makes iteration order and side effects entangled.

Function Composition

pipe and compose are themselves higher-order functions: they take functions in and return a new function.

Currying

Reshapes a multi-argument function into a chain of one-argument functions — which makes passing functions into HOFs like pipe much more practical.

Partial Application

Fixing some of a function's arguments ahead of time, producing a new, smaller function — a direct use of "returns a function."

Point-Free Style

Writing a pipeline of HOFs without ever naming the data flowing through it.
