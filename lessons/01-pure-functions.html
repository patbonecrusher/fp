Pure Functions

The single idea almost everything else in functional programming is built on top of.

What it is

A function is pure when it satisfies two rules:

  1. Same input → same output, always. No randomness, no reading the clock, no reading a global variable that might have changed.
  2. No side effects. It doesn't mutate its arguments, doesn't write to the console/disk/network, doesn't touch any variable outside its own scope.

If you can't predict a function's return value just by looking at the arguments you're passing it, it isn't pure.

Why it matters

  • Testable — assert on input/output pairs, no setup or mocking required.
  • Predictable — you can reason about a call in isolation, without reading the rest of the file.
  • Cacheable — a pure function can be memoized safely, since the same input will never need recomputing.
  • Parallel-safe — no shared mutable state means no race conditions between calls.
  • Refactor-safe — move it, inline it, call it twice instead of once — nothing breaks elsewhere.

Impure code doesn't just risk bugs — it hides them. The bug lives wherever the hidden state was last changed, which can be nowhere near the function that misbehaves.

Before / after

✗ Impure

let taxRate = 0.08; // shared, mutable

function addItemImpure(cart, price) {
  cart.total += price * (1 + taxRate);
  return cart.total; // mutates its argument
}

✓ Pure

function priceWithTax(price, rate) {
  return price * (1 + rate);
}

function addItemPure(cart, price, rate) {
  return { total: cart.total + priceWithTax(price, rate) };
}

Watch it break

Two calls that look identical at the call site (addItemImpure(cart, 10)) give different results, because taxRate changed somewhere else in the program between them:

let cartA = { total: 0 };
addItemImpure(cartA, 10);
// taxRate changes elsewhere in the codebase...
let cartB = { total: 0 };
addItemImpure(cartB, 10);

Actual output when you run the lesson script:

Impure cart after adding $10 item: 10.8 Impure cart after adding another $10 item: 12 <-- same call, different result Pure: original cart is untouched: 0 Pure: new cart has the item: 10.8 Pure: same inputs always give the same output: true

The pure version can never produce that surprise: every input it depends on (price, rate, the cart itself) is right there in the argument list, and the original cart is left untouched rather than mutated.

Related concepts

Referential Transparency

Really the same property stated differently: a pure call can be swapped for its return value with no change in behavior.

Immutability

Purity requires not mutating arguments; immutable data makes that a guarantee instead of a rule you have to remember.

Side Effects

Purity is defined as the absence of side effects — this is the term it's contrasted against.

Idempotence

Related but distinct: f(f(x)) === f(x). A function can be pure but not idempotent, or idempotent but not pure.

Memoization

Only safe on pure functions — it assumes "same input → same output" will hold forever.

Function Composition

Composing pure functions keeps the whole pipeline pure; one impure link breaks the guarantee downstream.
