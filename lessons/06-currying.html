Currying

Give a function part of its input now, get back a specialized function waiting for the rest.

What it is

Picture a two-question form that normally shows both questions on one page: "what's your rate?" and "what's your price?" Currying splits that into two separate pages — answer the first question, and you're handed a new, smaller form that only asks the second. You can even hand that half-filled form to someone else to finish.

In code: a normal function f(a, b) wants both arguments at once. A curried version, f(a)(b), takes a first and returns a brand-new function that's still waiting for b. Nothing is computed until the last argument arrives.

const applyDiscount = (rate) => (price) => price * (1 - rate);

applyDiscount(0.1);       // => a function, waiting for `price`
applyDiscount(0.1)(50);   // => 45, now it runs

Why it matters

Lesson 5 showed functions that return functions as the mechanism for reuse. Currying applies that mechanism on purpose, to every argument, which pays off specifically where Lesson 4's pipe needs it: every step in a pipe can only pass one value through. A curried function already takes one argument at a time, so it slots into a pipe directly — an un-curried, multi-argument function needs a hand-written wrapper for every case you need.

  • Specialized functions, free — applyDiscount(0.1) hands back a ready-to-use "10%-off" function, with no wrapper to write.
  • Configuration becomes data — a new rate, region, or rule is a new row of data, not a new function someone has to hand-write (and risk getting wrong).
  • Plays directly with pipe/compose — curried functions are exactly the one-argument shape those HOFs expect.

Before / after

✗ Un-curried, hand-written wrapper per case

const applyDiscount = (rate, price) =>
  price * (1 - rate);

// pipe only passes ONE value, so:
const applyUSDiscount = (price) =>
  applyDiscount(0.10, price);

✓ Curried, no wrapper needed

const applyDiscount = (rate) => (price) =>
  price * (1 - rate);

// fits directly into pipe:
pipe(applyDiscount(0.10), addTax(0.08))

Watch it break

The setup: a pricing pipeline needs a discount and tax rate per region. With un-curried functions, each region needs its own hand-written wrapper to get down to the one-argument shape pipe requires. Adding Japan means copy-pasting the US wrapper pattern — and someone forgets to change the rate:

const applyUSDiscount = (price) => applyDiscount(0.10, price);
const applyJPDiscount = (price) => applyDiscount(0.10, price); // bug: copied from US, should be 0.05

Actual output when you run the lesson script:

Un-curried, hand-written wrappers per region: US total for $100: 97.2 JP total for $100 (should use a 5% discount): 99.00000000000001 <-- wrong, copied the US discount rate Curried, a region is just a row of data: US total for $100: 97.2 JP total for $100: 104.50000000000001 applyDiscount(0.1) returns a function, not a number: true Calling it on $50 and $200: 45 180

With the curried version, a region is just an entry in a regions table — applyDiscount(regions.JP.discount) builds the specialized function on the spot. There's no wrapper function to copy-paste, so there's nothing to get wrong when a new region shows up.

Related concepts

Higher-Order Functions

A curried function is a HOF by construction — every call except the last one returns another function.

Function Composition

Currying is what makes a multi-argument function usable inside a pipe/compose chain, which only passes one value per step.

Partial Application

The general idea currying is a specific, disciplined version of: fixing some of a function's arguments ahead of time to get a smaller function back.

Point-Free Style

Curried, composable functions are what make it possible to define a pipeline without ever naming the data flowing through it.
